3. Positioning

1. Flagship customer

Who: a developer who works with a coding agent every day on a repository with several modules.

What they lose today: every session starts from zero. They paste the same rules into every prompt, or they keep one long AGENTS.md that the agent reads for every task, where the rule that matters gets buried (site/home.txt, levels 1 and 2).

What changes: the agent writes and keeps its own notebook in the repo, one short contract per part of the codebase, opens only the right page for each task, and adds what review taught it after every job (F-005, F-007, F-016).

The home page talks to this person first. Tech leads and platform engineers come after.

Your AGENTS.md is too long. Give your agent a notebook instead.

You started with a short AGENTS.md. A few rules, the test command, the folder layout. Then the agent rounded a refund with floats, so you added a line about cents. Then it called the payment API directly, so you added a line about the service layer. Six months later the file is hundreds of lines long, and the agent reads all of it for every task, including the one-line typo fix.

The rule that would have saved you today is in there. It is just buried.

The problem is not the rules. It is that there is one file.

A single root file has two jobs that pull against each other. It has to hold everything the agent might need, and it has to be short enough that the agent pays attention to the part that matters. It cannot do both.

So most of us end up doing one of two things: paste context into each prompt (and you become the memory), or keep growing the file (and the file becomes the memory, with every task paying for all of it).

There is a third way: let the agent keep a notebook, with one short page per part of your project and a table of contents at the front.

What the notebook looks like

workflow-blueprint is a meta-skill: a skill that teaches your agent to write other skills for your repository. You install it once and ask for the notebook:

npx skills add devton/agentic-workflow-blueprint
blueprint this project.

The agent asks you five things: a short name for the project, the base branch, the stack, which workflows you want, and your hard rules. Then it writes skills/<project>/:

MEDIA M1 (screenshot slot)
  • SKILL.md, the orchestrator: how to classify a task and pick one workflow.
  • reference/routing-matrix.md, the table of contents: which kind of task goes to which page.
  • workflows/<name>/SKILL.md, one contract per workflow you asked for.
  • template.json, the same command list for tools that read JSON.

Your AGENTS.md keeps a short "Start here" link to the new skill. It stops being the place where every rule lives.

One page per task: where the time savings come from

From then on, when you type /<project> <command>, the agent loads only that workflow's contract. A bug fix in checkout does not load your infrastructure notes. That is the whole trick: the notebook is organized so that each task reads one page, not the whole book.

Each page has the same sections: Goal, Scope, Triggers, Inputs, Invariants, Procedure, Outputs, Review gate and References. Invariants are the rules that must never break, like "amounts are integers in cents". The Review gate is a pass/fail checklist at the end. If the gate fails, the work is not done.

MEDIA M2 (screenshot slot)

The notebook corrects itself

A notebook you have to maintain by hand would just move the problem. So the bundled radioactive workflow ends every job with a phase that does it for you. Phase 10 reviews what the run discovered and writes new patterns and constraints back into the contracts it used.

That is the moment the site shows in red: a review caught float rounding on refunds, and the next version of the payments contract has a new invariant. The next time anyone asks for payment work, that rule is on the page the agent opens. You did not have to remember to add it.

This is where the reduced anxiety comes from. You are no longer the only thing standing between a rule you learned last month and the agent forgetting it today.

It lives in your repo, so you can read it

Lessons are plain markdown, next to your code. You can read them, edit them in conversation, or delete one that is wrong. They change in commits like everything else, and they persist beyond a single chat session.

FAQ

Does it replace my AGENTS.md?

No. Your root doc stays, but short: it links to skills/<project>/SKILL.md and the agent follows the link. The detail moves into the contracts.

Which workflows should I ask for first?

Start with what you do every week. The repo ships 46 contract templates (document, review, radioactive, plan-to-blueprint, infra and security ones) meant to be copied and adapted.

What if the agent writes a bad rule?

It is a line of markdown in your repository. Read it in the diff, edit it, or delete it.

Do I have to use radioactive?

No. Routing and contracts work on their own. radioactive adds the phase that writes lessons back.

How do I test it without touching my main branch?

Run it on a branch. Everything it writes is files you can review before you merge.

Five people on your team use coding agents. Each one has a slightly different prompt, a slightly different set of pasted rules, and a slightly different idea of how the payment module works. You find out in review, one pull request at a time.

The fix is not a longer style guide. It is putting the agents' rules where the team already agrees on things: in the repository, changed through pull requests.

Rules your team can see

workflow-blueprint writes a folder of contracts into your repository, skills/<project>/, one per kind of work. Each contract has the same sections: Goal, Scope, Triggers, Inputs, Invariants, Procedure, Outputs, Review gate and References.

That sameness is the point for a lead. When a contract says "All calls go through PaymentService" under Invariants, every agent that opens the payments contract reads that line. It is not in anyone's private prompt. It is in a file the whole team can read, which is what transparency means here: you can see exactly what the agents are told.

Lessons arrive as diffs you review

The bundled radioactive workflow runs eleven phases in order: classify, discover, UX design (if there is UI), plan, blueprint, execute, tests, review, fix loop, blueprints, changelog. Two of its gates matter for a team:

  • It stops after discovery questions and after the plan, and waits for a person to answer or approve before it writes code.
  • Phase 10 writes what the run discovered back into the contracts. So when an agent learns something, the lesson shows up as a change to a markdown file in the same branch.

Your normal review now covers both: the code, and the rule the agent wants to keep. If the lesson is wrong, you say so in review, like any other line. That is risk reduction you already know how to run, because it is just your pull request process.

Start from your plan, not a blank page

Most leads already have a plan for the next quarter's work. The plan-to-blueprint workflow takes a technical plan (milestones, tasks, acceptance criteria, constraints) and turns it into project skills with router commands and a manifest. Acceptance criteria become review gates, which turns "done" into pass or fail checks instead of a feeling.

For bigger, domain-heavy work there is embed-aihero-radioactive: fourteen phases that add Matt Pocock / AI Hero skills (wayfinder, grilling, domain-modeling, research, prototype, to-spec), and always run your project skill first.

The notebook travels with the repository

Because the contracts are committed, a new teammate who clones the repository gets them on day one, and so does every agent they use. The root doc keeps a "Start here" link to the project skill. Nobody has to send a prompt file around.

When the setup is right, the team ships changes that were reviewed, tested and documented, with a changelog at the end of each radioactive run. That is the reputational assurance part for you as a lead: what leaves your team looks the same, whoever's agent wrote it.

Why a contract and not a prompt: risk reduction

Every one of these is a contract with the same sections: Goal, Scope, Triggers, Inputs, Invariants, Procedure, Outputs, Review gate and References. The Procedure is a fixed sequence, so two runs do the same thing. The Review gate is a pass/fail list. If it fails, the work is not done.

When the change goes through the radioactive lifecycle, one more rule applies: work that touches network, infrastructure, IaC or OS baselines must include an explicit rollback, align with a change window and validate health after the change.

These workflows describe authorized checks on systems you own or are allowed to test.

Fits the tools you already run: integration

The contracts are named after the tools, so they route like any other task. Once a Trivy contract is in your skills/<project>/workflows/, a request like "scan the release image" is classified by the routing matrix and loads that one page, not your whole runbook folder.

They are templates: copy, rename and adapt them to your thresholds and your registry. Your version is plain markdown in your repository.

Parte 1. Posicionamento

Quem somos

workflow-blueprint é uma meta-skill para agentes de código: um conjunto de arquivos markdown que o agente instala e segue para escrever as skills do próprio projeto do usuário. Em vez de um AGENTS.md gigante, o agente passa a ter um caderno: uma página curta por parte do código, um índice na frente, e uma regra nova a cada revisão.

A promessa: "We teach your agent to keep a notebook of your project, so you stop explaining the same rules every session."

Para quem falamos primeiro

Para a pessoa desenvolvedora que trabalha com um agente de código todo dia, num repositório com vários módulos. Ela perde tempo reexplicando as mesmas regras a cada sessão, ou mantém um AGENTS.md enorme que custa tokens em toda tarefa e esconde a regra que importa.

Depois dela, e nessa ordem: tech leads de times que usam agentes, e engenheiros de plataforma e segurança.

As personas, de dois jeitos

Por conta própria

  • Dev com agente de código: quer parar de reexplicar o projeto. Primeiro valor: a segunda tarefa já abre só o contrato certo, sem pedir contexto.
  • Engenharia de plataforma e segurança: quer que mudanças de infra e checagens de segurança sigam sempre os mesmos passos, com rollback. Primeiro valor: um contrato de Trivy ou Kubernetes copiado roda o gate no repositório dela.

Com o mantenedor

  • Tech lead: quer que o agente de cada pessoa do time siga as mesmas regras, revisadas como código. Primeiro valor: o primeiro pull request em que uma lição do agente é revisada por uma pessoa.

Essa divisão é interna. Nenhuma página fala em "self-serve" ou "assistido".

Princípios
  1. Vendemos a facilidade da segunda execução, não da primeira.
  2. Mostramos os arquivos de verdade antes de prometer qualquer coisa.
  3. Falamos do trabalho da pessoa, não do nome da funcionalidade.
  4. Frases curtas, sem hype, sem números que não podemos mostrar.
  5. Todo convite é o mesmo: "Install the blueprint" com o comando npx skills add devton/agentic-workflow-blueprint.

# Workflows of the running machine

workflow "article_batch" {
  inputs = [source.workspace, "articles/index.json", source.product_repo]

  step "pick_gaps" {
    does = "Coverage persona x stage x loop x value element; pick the gaps first"
  }

  step "draft" {
    does = "Write 3 ready articles, at least 2 from the sales lane, with value, loop hook, CTA and FAQ"
    uses = [rule.cta, rule.never_say, rule.facts_only, rule.no_names]
  }

  step "audit" {
    does = "Run value-audit on each article"
    uses = [agent.auditor]
  }

  outputs     = ["articles/<date>/*.md", "articles/index.json"]
  review_gate = gate.content
}

workflow "release_sweep" {
  inputs = [source.product_repo, source.site]

  step "explore_delta" {
    does = "Update product-map.md: new, changed and removed workflows, with evidence"
    uses = [rule.rollout_honesty, rule.facts_only]
  }

  step "site_drift" {
    does = "List site claims the new ledger no longer supports (counts, removed workflows)"
  }

  step "lane_a" {
    does = "Draft one release-driven article and an integration page spec if a tool shipped"
    uses = [rule.cta, rule.never_say, rule.regulated_security]
  }

  outputs     = ["product-map.md", "articles/<date>/*.md", "landing/integration-<slug>.md"]
  review_gate = gate.content
}

workflow "adoption_sweep" {
  inputs = [source.github_activity, source.public_notebooks, source.install_counts]

  step "record_milestones" {
    does = "Record installs, scaffolds, lessons and team requests with their real dates"
  }

  step "check_signals" {
    does = "Evaluate signal.notebook_alive and signal.team_request"
  }

  step "measure" {
    does = "Compute stage conversions, days between stages and loop strength; list what could not be measured"
  }

  outputs     = ["sales-machine/metrics/<date>.md"]
  review_gate = gate.metrics
}

workflow "lead_note" {
  inputs = [source.github_activity, source.public_notebooks]

  step "build_note" {
    does = "What they built, which workflows, which tools, which lane; public facts only"
    uses = [rule.no_contact]
  }

  outputs     = ["lead note for the maintainer"]
  review_gate = gate.lead
}

workflow "coverage_review" {
  inputs = [source.workspace]

  step "matrix" {
    does = "Persona x stage and value element x persona counts; mark empty cells"
  }

  step "next_batch" {
    does = "Propose the next article and page topics from the gaps"
  }

  outputs     = ["sales-machine/coverage/<date>.md"]
  review_gate = gate.content
}

workflow "rule_change_sweep" {
  inputs = [source.workspace]

  step "reaudit" {
    does = "Run value-audit on every existing article, spec and manual chapter against the new config"
    uses = [agent.auditor]
  }

  step "fix_with_history" {
    does = "Fix failing files, keeping the previous version in history/<file>-<date>"
  }

  outputs     = ["audit/findings.json", "history/"]
  review_gate = gate.content
}

workflow "report_refresh" {
  inputs = [source.workspace]

  step "spec_check" {
    does = "Self-check this spec: braces, block types, references, no forbidden blocks"
  }

  step "build" {
    does = "Write the self-contained HTML report from every workspace file"
  }

  outputs     = ["report/sales-machine-report.html"]
  review_gate = gate.report
}
